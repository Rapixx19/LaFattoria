## Data Flow

```
Client Browser / Mobile
        │
        ▼
   Next.js App Router
        │
   ┌────┴────────────────────────┐
   │ Server Components            │  ← fetch data on server, no API round-trip
   │ Route Handlers (api/)        │  ← PDF gen, push subscribe, webhooks
   │ Server Actions               │  ← form mutations
   └────┬────────────────────────┘
        │
        ▼
   packages/supabase
        │
   ┌────┴────────────────────────┐
   │ Supabase Postgres            │  ← all persistent data
   │ Supabase Auth                │  ← sessions, RLS identity
   │ Supabase Realtime            │  ← booking status changes
   │ Supabase Storage             │  ← horse photos, invoice PDFs
   │ Supabase Edge Functions      │  ← push notifications, async jobs
   └─────────────────────────────┘
```

## Auth Architecture

### Owner / Trainer App
- Email + password login via Supabase Auth
- Role stored in `profiles.role` (`owner` | `trainer`)
- Middleware checks role on every protected route
- Session stored in httpOnly cookie (next/supabase SSR)

### Client App
- Magic link (passwordless) OR email + password
- Client linked to their `clients` table row via `profiles.client_id`
- Can only access their own data (enforced by RLS)

### RLS Summary
```
owners     → full access to all tables
trainers   → read all, write bookings + horses, no billing
clients    → read/write own bookings, read own bills/horse
```

## Supabase Realtime Usage

Keep realtime subscriptions minimal to avoid complexity:

| Event | Channel | Who subscribes |
|---|---|---|
| New booking request | `bookings:status=requested` | Owner app — Richieste page |
| Booking status change | `bookings:id=<id>` | Client app — booking detail |
| New announcement | `announcements` | Client app — home page |

## PDF Generation

Invoice PDFs are generated server-side via a Next.js route handler:

```
GET /api/bills/[id]/pdf
  → fetch bill from Supabase (server, using service role)
  → render with packages/pdf/invoice-doc.tsx
  → stream PDF response with Content-Disposition: attachment
  → optionally store in Supabase Storage for client download
```

## Push Notification Flow

```
1. User grants permission on PWA install
2. Browser generates push subscription
3. App calls POST /api/push/subscribe → stored in push_subscriptions table
4. Server event triggers → Supabase Edge Function → Web Push API → device
```

## Module Boundaries

Features must NOT import from each other directly.
Communication happens only through:
- Supabase database (shared source of truth)
- Shared packages (ui, utils, supabase, pdf)
- Next.js route handlers (for async triggers)

```
✅ CORRECT:  features/billing  →  packages/supabase  →  DB
✅ CORRECT:  features/revenue  →  lib/queries/bills.ts  →  DB
❌ WRONG:    features/revenue  →  features/billing (direct import)
```

## Deployment (Vercel)

Two separate Vercel projects from the same monorepo:

```
Project: lafattoria-owner
  Root dir: apps/owner
  Domain: app.lafattoria.ch

Project: lafattoria-client
  Root dir: apps/client
  Domain: mio.lafattoria.ch
```

Supabase project is shared between both apps.
